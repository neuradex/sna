SNA는 대화 히스토리를 SQLite 안의 **정규화 블록** 평탄 시퀀스로
저장한다. 각 블록은 두 개의 직교 축을 가짐:

- `actor`: `user` | `assistant` | `system`
- `kind`: `text` | `thinking` | `tool_use` | `tool_result` | `status` | `error`

바이너리 콘텐츠(이미지, 파일)는 id 기반 별도 `embeds` JSON에 두고,
블록의 `content` 텍스트는 인라인 `![](embed://<id>)` 참조를 갖는다.
프로바이더 네이티브 모양(Anthropic content array, Codex
`ResponseItem`, OpenCode parts)은 **요청 시 파생**되는 것이지 진실의
원천이 아니다.

## 왜 플랫 블록인가

대부분의 프로바이더는 text, tool_use, thinking을 하나의 "message"
객체 안에 묶는 중첩 메시지 포맷을 쓴다. 단일 프로바이더에서는 잘
돌지만 크로스 프로바이더 replay에서는 골치가 아프다. 모든 프로바이더가
순서, signature, optional 필드 규칙이 살짝씩 다르기 때문.

평탄 블록 리스트는 세 런타임 모두 라운드트립이 가능한 최소 표현이다.
각 프로바이더의 어댑터가 평탄 리스트를 걸으면서 그 프로바이더가
기대하는 중첩 모양을 재구성한다.

## Replay 어댑터

| 경로 | 어댑터 |
|------|--------|
| `claude-code` resume | `history/claude-code.ts` (`thinking.signature` 보존하는 JSONL) |
| `codex` resume | `history/codex.ts` (`thread/resume` + `ResponseItem[]`) |
| `opencode` resume | `history/opencode.ts` (prompt-prelude 재구성) |

`POST /agent/resume`이 갓 spawn된 프로세스에 히스토리를 replay하는
방식이다. 입력은 세션 id와 정규화 블록뿐. 어댑터가 프로바이더별 함정
(signature 필드, tool_use 순서, partial-text 합치기)을 다 처리한다.

## 3계층 어트리뷰션

모든 블록은 세 가지 어트리뷰션 차원을 기록한다:

- `provider`: 블록을 만든 런타임 (claude-code / codex / opencode)
- `modelProvider`: 모델을 소유한 벤더 (anthropic / openai / google)
- `model`: 정확한 슬러그 (`claude-sonnet-4-6`, `gpt-5.4` 등)

이로써 유저가 스레드 도중 프로바이더를 바꿔도 행 단위 진실을 잃지
않고 UI가 "여기서 Codex의 gpt-5.4로 갈아탔습니다" 같이 렌더할 수
있다.

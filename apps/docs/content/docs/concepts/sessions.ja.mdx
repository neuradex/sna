**SnaSession** はコンシューマアプリが知っている永続的なもの (安定
した id、ラベル、cwd、meta)。**RuntimeSession** はそのセッションに
マウントされた具体的なランタイム設定 1 つ: provider、model、
permission mode、MCP サーバ、hooks。SnaSession 1 つは寿命の中で複数
の RuntimeSession をマウントでき、**runtime chain** はそのセッション
が身につけたすべての設定の順序付き履歴だ。

## なぜ 2 層か

ユーザが Claude Code でチャットを始め、スレッド途中で Codex に切り
替え、それから reasoning レベルを上げたら、それは SnaSession 1 つに
対する 3 つの異なる RuntimeSession になる。アトリビューションが行
ごとに正直なまま維持され、replay 時に各ランタイムのネイティブ履歴
を以前のターンを失わずに再構築できる。

## ライフサイクル

```
POST /agent/sessions      → SnaSession 作成 (プロセスなし)
POST /agent/start         → 初期 RuntimeSession マウント、プロセス spawn
POST /agent/send          → メッセージ送信、イベント流れる
POST /agent/set-model     → インプレース上書き または 新 RuntimeSession
PATCH /agent/session      → {cwd, model, permissionMode} 統一 mutator
POST /agent/resume        → プロバイダネイティブ履歴を再構築、respawn
POST /agent/restart       → 同じ設定で respawn (そのまま保持)
POST /agent/kill          → プロセスを止める (セッションレコードは残る)
DELETE /agent/sessions/:id → セッション + 履歴を削除
```

## PATCH 意味論

`PATCH /agent/session` は統一 mutator。サーバはアクティブな
プロバイダの `applyPatch()` フック経由で各フィールドを適用する。
このフックがインプレース適用と respawn-with-history-replay のどちら
を取るかを決める:

| フィールド | claude-code | codex | opencode |
|------------|-------------|-------|----------|
| `model` | インプレース | per-turn 上書き | インプレース |
| `permissionMode` | インプレース | per-turn 上書き | インプレース |
| `cwd` | respawn + replay | インプレース (per-thread cwd) | respawn |

レスポンスの `applied` フィールドがどの経路を通ったか教えてくれる
ので、クライアントは必要な時だけ "reloading…" のような表示を出せる。

## なぜ重要か

ほとんどの「エージェントプラットフォーム」抽象は、何かを変えるには
セッションを破壊することを強いる。SNA は設定をセッションレコードの
一級の軸として扱うので、下層のランタイム設定が変わっても UX を
切れ目なく続けられる。

SnaSession 1 つは寿命の中で複数の RuntimeSession をマウントできます。
**runtime chain** はそのセッションが身につけたすべての設定の順序付き
履歴です。履歴は正規化されています。プロバイダネイティブの形は replay
ごとに派生するため、ランタイム切り替えは respawn として処理されます。

## 切り替え

```ts
// Claude Code で開始
await client.agent.start(sessionId, {
  provider: "claude-code",
  model: "claude-sonnet-4-6",
});

// ...ターンが進行し、履歴が積み上がり...

// 会話を保ったまま Codex に切り替え
await client.agent.patch(sessionId, { provider: "codex", model: "gpt-5.4" });
```

`provider` フィールドを持つ `PATCH /agent/session` は現在のプロセス
を倒し、新ランタイムで respawn し、正規化履歴を新プロバイダのネイティブ
形に replay します。セッションレコード、イベントカーソル、runtime chain
はすべて維持されます。

## Resume vs restart

| 操作 | プロセス | 履歴 |
|------|----------|------|
| `restart` | 同じ設定で respawn | replay しない (warm restart) |
| `resume` | 同じ設定で respawn | 再構築して再注入 |
| `patch` (プロバイダ変更) | 新設定で respawn | 新プロバイダ用に再構築 |

長いアイドル後やランタイムが終了したときは `resume` を使います。
コンシューマがランタイム切り替えを必要とするときは `patch` を使います。

## なぜ重要か

ほとんどの「エージェントプラットフォーム」抽象は、会話をランタイム
ごとの一時的状態として扱います。プロセスを失うとスレッドも失います。
SNA では正規化履歴が真実の源です。すべてのプロバイダはプラグイン可能な
replay ターゲットであり、記憶の保管者ではありません。

## 注意

- **ホスト型ツールの状態は引き継がれません。** Codex の画像生成、
  web_search といったホスト型ツールはプロバイダ側に存在します。前回
  呼び出しの `tool_result` は履歴にあるが、次のターンが前回の OpenAI
  会話 id を期待する場合、その状態は失われています。
- **モデル固有のトークンは replay で一部失われます。** Claude の拡張
  thinking `signature` は Claude→Claude replay では保持されるが、
  Codex に切り替えると破棄されます(対応する概念がないためです)。
- **コストアトリビューションはターンごとに正確に維持されます。** 3 層
  アトリビューション (provider × modelProvider × model) が行ごとに
  記録されますので、事後分析がランタイム別の使用量を明確に分割できます。
